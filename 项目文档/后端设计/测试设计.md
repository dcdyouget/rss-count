# 测试设计

## 测试策略

- **TDD 原则**：先写测试，再写实现。测试 → 红灯 → 实现 → 绿灯 → 重构。
- **测试分层**：单元测试（纯逻辑，不依赖 IO）→ 集成测试（真实 SQLite + HTTP，Mock 外部依赖）
- Quarkus 测试支持：`@QuarkusTest` + 独立测试 Profile + `@TestTransaction` 自动回滚
- 测试数据库：每次测试类使用独立临时 SQLite 文件

---

## 一、单元测试

纯 Java 逻辑，无 IO 依赖，快速执行。

### U1. SimHash 算法

| 用例 ID | 测试内容 | 输入 | 预期 |
|---|---|---|---|
| U1-1 | 相同文本汉明距离为 0 | `computeSimHash("北京今日天气晴好")` 两次 | 距离 = 0 |
| U1-2 | 相似文本汉明距离 ≤ 3 | "北京今日天气晴好" vs "北京今天天气晴好" | 距离 ≤ 3 |
| U1-3 | 不同文本汉明距离 > 3 | "北京今日天气晴好" vs "Python 3.13 发布" | 距离 > 3 |
| U1-4 | 空字符串 | `computeSimHash("")` | 不抛异常 |
| U1-5 | 纯英文 | "Hello World This Is A Test" | 正常计算 |
| U1-6 | 纯数字/符号 | "12345!@#$%" | 正常计算 |
| U1-7 | 长文本（>1000字） | 构造长文本 | 正常计算，不超时 |

### U5. 时间规范化

| 用例 ID | 测试内容 | 输入 | 预期 |
|---|---|---|---|
| U5-1 | RFC 822 | `Tue, 20 May 2026 10:30:00 +0800` | UTC+8 正确 |

## 二、集成测试

依赖真实 SQLite（临时文件），Mock 外部 HTTP 调用（RSS/AI）。

### I1. 任务全生命周期（黄金路径）

| 用例 ID | 测试内容 | 验证点 |
|---|---|---|
| I1-1 | 创建任务 → RUNNING | POST /tasks 返回 201，task.status=RUNNING，report 已创建 |
| I1-2 | 拉取阶段 | Mock 3 个 RSS 源各返回 5 条新闻 → 验证 News 表有 15 条（假设无重复） |
| I1-3 | 格式化阶段 | 验证 News.structuredContent 非空，simHash 已计算 |
| I1-4 | 任务完成 | task.status=COMPLETED，report.newsCount 正确 |
| I1-5 | SSE 消息 | 订阅 SSE → 收到 progress(多次) → complete(一次)，消息序列正确 |

### I2. 去重

| 用例 ID | 测试内容 | 验证点 |
|---|---|---|
| I2-1 | 同 URL 去重 | Mock 同一 URL 出现 3 次 → News 表只有 1 条 |
| I2-2 | 保留更长正文 | 第 1 次 contentLength=100，第 2 次=300 → 保留 300 的 |
| I2-3 | 跨任务不去重 | 两个任务拉取同 URL → 各自有 1 条 News |

### I3. AI 降级

| 用例 ID | 测试内容 | 验证点 |
|---|---|---|
| I3-1 | AI 超时 | Mock AI 返回超时 → summary 为空，任务仍 COMPLETED |
| I3-2 | AI 返回错误 | Mock AI 返回 500 → summary 为空，任务仍 COMPLETED |

### I4. RSS 源容错

| 用例 ID | 测试内容 | 验证点 |
|---|---|---|
| I4-1 | 单个源超时 | 3 个源中 1 个超时 → 跳过该源，其他 2 个正常拉取 |
| I4-2 | 全部源失败 | 所有源超时 → task.status=FAILED，SSE error 事件 |

### I5. RSS 源 CRUD

| 用例 ID | 测试内容 | 验证点 |
|---|---|---|
| I5-1 | 添加源 | POST → 201，name 从 RSS XML 解析 |
| I5-2 | URL 重复 | POST 同 URL → 409 |
| I5-3 | 软删除 | DELETE → isActive=false，列表不包含 |
| I5-4 | OPML 导入 | 上传 OPML 文件 → 返回 created/skipped 统计 |
| I5-5 | OPML 导出 | GET → 下载 XML，再导入 → 数据一致 |

### I6. 稿件

| 用例 ID | 测试内容 | 验证点 |
|---|---|---|
| I6-1 | 创建稿件 | POST → 201，关联 News 正确 |

| 用例 ID | 测试内容 | 验证点 |
|---|---|---|

### I8. 定时任务

## 三、TDD 编写顺序

按开发阶段排序，每个阶段的测试先写，然后写实现：

### 阶段 1：基础设施
1. U1 SimHash 算法测试 → 实现 SimHash
2. U2 TextCleaner 测试 → 实现 TextCleaner
3. U5 时间规范化测试 → 实现时间工具
4. U6 OPML 解析测试 → 实现 OPML 工具

### 阶段 2：数据层
5. 创建所有 Entity 类（无需测试，Panache Entity 框架提供）
6. I5 RSS 源 CRUD 测试 → 实现 Controller + Service
7. I7 设置测试 → 实现 Settings 功能

### 阶段 3：核心业务
8. U3 去重逻辑单元测试 → 实现去重
9. U4 结构化正文测试 → 实现 ContentExtractor
10. I1 任务全生命周期测试 → 实现 TaskExecutor + RssFetchService + NewsFormatService
11. I2 去重集成测试 → 完善去重
12. I4 容错测试 → 错误处理

### 阶段 4：AI + 进阶
13. I3 AI 降级测试 → 实现 AiService
14. I1-5 SSE 测试 → 实现 SSE 推送
15. I6 稿件测试 → 实现 DraftService + 生成

### 阶段 5：定时 + 仪表盘
16. I8 定时任务测试 → 实现 TaskScheduler
17. I9 仪表盘测试 → 实现 Dashboard

## 四、测试运行

```bash
# 单元测试（快速，无 IO）
./mvnw test -Dtest="SimHashTest,TextCleanerTest,..."

# 集成测试（需要 SQLite）
./mvnw verify -Dquarkus.test.profile=test

# 全量测试
./mvnw verify
```
